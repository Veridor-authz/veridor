The Job is an Argo CD {{ include "veridor-gate.argoList" .Values.hook.argocd.phase }} hook with no fixed name (metadata.generateName):
Argo CD creates one per sync that runs hooks, once the sync's resources are Healthy, named
{{ include "veridor-gate.argocdJobPrefix" . }}<revision>-postsync-<the sync's start, Unix seconds>
(<revision>: its first 7 characters; empty for an Application with several sources),
and a failed Job fails that sync's operation. Each sync reads its own Job; with
one fixed name Argo CD v3.5.3 had reported syncs from the previous sync's Job.
A selective sync or an Apply Only sync runs no hooks: it creates no gate Job and
still ends Succeeded, with no PostSync entry in its syncResult.

Only Argo CD renders this mode. `helm install` and `helm upgrade` refuse it:
the Helm CLI does not run Argo CD hooks, so it would apply the Job as a plain
resource and report the release deployed whatever the gate found. These notes
come from a dry run. Deploy the chart through an Argo CD Application; with the
Helm CLI, use hook.mode helm.

The Job a sync ran is the PostSync entry of the Application's
status.operationState.syncResult.resources. Read its log:

  job="$(kubectl -n argocd get application <app> -o jsonpath='{.status.operationState.syncResult.resources[?(@.hookType=="PostSync")].name}')"
  kubectl -n {{ .Release.Namespace }} logs "job/${job}"

A plain Job. Nothing here waits for it: whatever applied it must wait for
this Job's own outcome, Complete or Failed, and pass only on Complete:

  while outcome="$(kubectl -n {{ .Release.Namespace }} get job {{ include "veridor-gate.jobName" . }} -o jsonpath='{.status.conditions[?(@.status=="True")].type}')"; do
    case " $outcome " in *" Complete "* | *" Failed "*) break ;; esac
    sleep 5
  done
  kubectl -n {{ .Release.Namespace }} logs job/{{ include "veridor-gate.jobName" . }}
  case " $outcome " in *" Complete "*) true ;; *) false ;; esac

Each `helm install` / `helm upgrade` is a new revision, so a new Job
(-r<revision>), and Helm removes the previous one. `helm template` always
renders revision 1: applied with `kubectl apply`, the Job is always -r1, and
re-applying it unchanged runs nothing while a wait reads the previous run.
Delete it first (README, "hook.mode none").
